# Java Persistence Lab

**Explore what happens between Java objects, SQL rows, and JSON documents.**

Java · JDBC · PostgreSQL · HikariCP · Jackson · JUnit Jupiter

A hands-on learning project for understanding persistence fundamentals before delegating them to an ORM.

## Overview

This repository explores the mechanics behind everyday data operations: acquiring connections, executing parameterized SQL, navigating result sets, assembling related objects, and managing transactions. Separate examples cover JSON mapping and in-memory aggregation.

The JDBC implementation uses explicit SQL and handwritten DAOs. It provides a practical foundation for understanding responsibilities that Hibernate and Spring Data JPA typically automate.

## What’s inside

| Area | Implemented examples |
| --- | --- |
| JDBC persistence | Create, read, and delete users and todos |
| Relationships | One user with many todos, reconstructed from `LEFT JOIN` results |
| Transactions | Explicit commit and rollback with auto-commit disabled |
| Connection pooling | A shared HikariCP datasource with a Prometheus metrics tracker |
| JSON mapping | Jackson serialization, deserialization, aliases, visibility, and property access |
| Aggregation | Group employees by department and calculate counts and salary totals |
| Tests | JUnit Jupiter tests for Jackson mapping behavior |

## Architecture

```text
JDBC Main
   │
   ▼
Repository interfaces & implementations
   │
   ▼
UserDao / TodoDao
   │
   ▼
HikariCP → JDBC connection → PostgreSQL
```

Repository implementations currently delegate to DAOs. DAOs own their connections, SQL statements, result mapping, and transaction completion.

The relationship is represented in two places:

```text
Java:       User.todos ←→ Todo.user
Database:   users.id   ←── task.user_id
```

`UserDao` groups joined rows by user ID using a `LinkedHashMap`. Each user is constructed once, while matching tasks are appended to that user’s todo collection. Users without tasks are retained by the left join.

## Getting started

### 1. Prerequisites

- A JDK compatible with the dependencies in `pom.xml`; the compiler currently targets Java 17.
- Maven available as `mvn`.
- A running PostgreSQL instance for the JDBC examples.

The JSON tests and aggregation example do not require PostgreSQL.

### 2. Configure the database connection

Edit [CustomDataSource.java](src/main/java/org/example/jdbc/config/CustomDataSource.java) to match your local database:

| Setting | Current configuration |
| --- | --- |
| JDBC URL | `jdbc:postgresql://localhost:5432/testing` |
| Username | `postgres` |
| Password | Configured directly in `CustomDataSource.java` |
| Auto-commit | `false` |

Connection settings are currently source-configured; environment-variable configuration is not implemented.

### 3. Create a local schema

No schema migration files are included. The following is a **suggested fresh-database schema** compatible with the current DAO queries. Run it against a new `testing` database:

```sql
CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    first_name VARCHAR(255),
    last_name VARCHAR(255),
    email VARCHAR(255)
);

CREATE TABLE task (
    id BIGINT PRIMARY KEY,
    name TEXT NOT NULL,
    user_id BIGINT NOT NULL,
    CONSTRAINT task_user_fk
        FOREIGN KEY (user_id)
        REFERENCES users(id)
        ON DELETE CASCADE
);
```

Task IDs are supplied by Java in the current implementation. Keep the task column order shown above while `TodoDao.add()` uses an insert without an explicit column list.

The suggested foreign key deletes a user’s tasks automatically when that user is deleted. This behavior is supplied by the database constraint; the Java delete method executes only the user deletion. An existing database may have different constraints.

### 4. Build

Run commands from the repository root:

```bash
mvn compile
```

### 5. Run an example

Run any entry point directly from your IDE, or prepare the dependency classpath:

```bash
mvn dependency:build-classpath -Dmdep.outputFile=target/classpath.txt
```

Then choose an example. The commands below use the macOS/Linux classpath separator.

| Entry point | Behavior |
| --- | --- |
| `org.example.jdbc.Main` | Deletes user ID `1`, then prints remaining users and their todos |
| `org.example.App` | Writes sample users to `hello.json`, then reads them back |
| `org.example.Custom` | Prints employee counts and salary totals by department |

```bash
# Database example — currently deletes user ID 1.
java -cp "target/classes:$(cat target/classpath.txt)" org.example.jdbc.Main

# JSON example — overwrites the sample JSON file.
java -cp "target/classes:$(cat target/classpath.txt)" org.example.App

# In-memory aggregation example.
java -cp "target/classes:$(cat target/classpath.txt)" org.example.Custom
```

The JSON entry point uses `src/main/java/org/example/hello.json` relative to the working directory, so launch it from the repository root.

## Creating a user and a todo

The existing repository API can be used as follows:

```java
UserDao userDao = new UserDao();
UserRepository users = new UserRepositoryImpl(userDao);
TodoRepository todos = new TodoRepositoryImpl(new TodoDao(), userDao);

User user = new User();
user.setFirstName("Ada");
user.setLastName("Lovelace");
user.setEmail("ada@example.com");

User savedUser = users.add(user);

Todo todo = new Todo(100L, "Explore JDBC relationships");
todo.setUser(savedUser);
todos.add(todo);
```

Use the entity classes from `org.example.jdbc.entity` and choose an unused task ID. These two repository calls commit independently; they do not form a single transaction.

## Tests

```bash
mvn test
```

The existing test sources exercise Jackson behavior:

- Public fields versus private fields with default visibility.
- Annotation-controlled field visibility.
- Property names, aliases, and read-only properties.
- Serialization and deserialization of stock objects.
- Rejection of unknown properties when explicitly configured.

There are currently no JDBC integration tests. Check Maven’s reported test count to confirm that its resolved Surefire version discovers the JUnit Jupiter tests.

## Project structure

```text
src/
├── main/java/org/example/
│   ├── App.java                  # JSON file round trip
│   ├── Custom.java               # Department aggregation
│   ├── entity/                   # Jackson example models
│   ├── enums/                    # JSON token experiments
│   └── jdbc/
│       ├── Main.java             # Database demonstration
│       ├── config/               # HikariCP datasource setup
│       ├── dao/                  # SQL, result mapping, transactions
│       ├── entity/               # User and Todo persistence models
│       └── repository/           # Interfaces and DAO delegates
└── test/java/org/example/entity/ # Jackson mapping tests
```

The two `User` classes serve different examples: `org.example.entity.User` is for JSON mapping, while `org.example.jdbc.entity.User` is for database operations.

## Learning roadmap

Natural next steps for extending this lab:

- Move transaction ownership into a service so several DAO calls can share one connection and commit atomically.
- Separate basic user queries from explicit relationship-loading queries.
- Batch-load collections for multiple users to explore the N+1 query problem.
- Make missing-record behavior and exception propagation consistent across DAOs.
- Add versioned schema migrations and PostgreSQL integration tests.
- Externalize connection settings and explicitly close the connection pool at shutdown.
- Experiment with an identity map and change tracking to understand persistence contexts and dirty checking.

These are extension ideas; the current project implements the explicit JDBC and JSON examples described above.
